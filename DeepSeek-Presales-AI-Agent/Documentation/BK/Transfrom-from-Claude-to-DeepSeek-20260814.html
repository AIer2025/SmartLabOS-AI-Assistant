（单文件为主，约半天工作量）

三句话结论

  1. 技术上很容易。 DeepSeek 提供了 Anthropic Messages API 兼容端点（https://api.deepseek.com/anthropic），本项目使用的 Anthropic C# SDK v12.34.1 支持自定义 BaseUrl（已在 DLL 中确认存在 set_BaseUrl），因此不需要更换 SDK、不需要重写流式解析、不需要重写工具循环。核心改动集中在 ClaudeAgentService.cs 一个文件。
  2. 质量总体持平，个别维度有增有减。 中文技术写作与长上下文检索大概率略升；40 轮工具循环的稳定性小幅下降（Terminal-Bench 2.0 相差约 1.5 个百分点）。真正的风险只有一个：本项目 SOUL.md 的第一原则是"严禁编造参数"，而 DeepSeek V4 系列在"不知道答案时倾向于继续作答而非承认不知道"这一维度上表现较弱，且在上下文含大量相似文本时更易出错 —— 而本系统的 system 前缀恰恰是 97 个高度同构的模块清单。
  3. 因此建议：迁移可以做，但必须同步把"防编造"从提示词约束升级为程序化校验。 现有的 VerifyDetailPhaseGrounding() 只检查"模型有没有回读过阶段一 HTML"，并不检查"文中的数字是否真的来自知识库卡片"。换模型之前，这层校验就该补上；换模型之后，它从"锦上添花"变成"必须项"。

⚠ 两点必须先说清楚的前提

  • DeepSeek 于 2026-08-16（本评估两天后）调价。 现价（V4 Pro：miss $0.435 / hit $0.003625 / out $0.87 每百万 token）将失效，新价按峰谷分时计费且整体上调。本文所有成本测算均以新价为基准，不用现价，避免决策建立在两天后就作废的数字上。
  • 峰段时段恰好覆盖中国工作时间。 官方标注峰段为 UTC 01:00–04:00 与 06:00–10:00，换算北京时间即 09:00–12:00 与 14:00–18:00。售前提案是典型的工作时段任务，所以成本预估应按峰段价（贵 50%）来做保守估算，把谷段价当作意外之喜而不是预算依据。

二、现状：本系统用了 Claude 的哪些能力

迁移的难度不取决于"调了几次 API"，而取决于"用了多少 Anthropic 专有特性"。下图是 ClaudeAgentService 对 Anthropic Messages API 的实际依赖面，以及每一项在 DeepSeek 兼容端点上的落地情况。

关键判断：依赖面里真正"卡脖子"的只有 output_config.format 一项，而它只用在模块选定这一步，且代码里已经写好了正则兜底（ModuleCatalog.ExtractFromText，见 ClaudeAgentService.cs:128-133）。也就是说，即使什么都不改直接切过去，最坏情况也是"模块选定偶尔要人工补选"，而不是整条流水线崩掉。

三、两条迁移路线

路线 A：走 Anthropic 兼容端点 推荐

做法：SDK 不换，只把 AnthropicClient 的 BaseUrl 指向 https://api.deepseek.com/anthropic，模型名改成 deepseek-v4-pro。

优点：工具循环、流式拼装、重试退避、ThinkingBlockParam 回传逻辑全部原样保留；StreamedTurn.cs（297 行，本项目最精细的一块代码）一行不用动；随时可以改回配置切回 Claude。

代价：受兼容层能力约束 —— 拿不到 DeepSeek 原生的 strict JSON Schema，也读不到 prompt_cache_hit_tokens 精确缓存计量。

路线 B：走 OpenAI 兼容原生端点

做法：换成 OpenAI SDK 或 Microsoft.Extensions.AI，调 /chat/completions。

优点：拿到全部原生能力 —— 严格模式函数调用（模块选定可恢复到强 Schema 约束）、prompt_cache_hit_tokens / miss_tokens 精确成本观测、reasoning_content 原生思考流。

代价：SSE 事件形状完全不同（delta.content / delta.reasoning_content / delta.tool_calls 分片），StreamedTurn 必须重写；重试异常类型判定也要重做。约 2–3 天，且回退到 Claude 需要维护两套调用层。

建议顺序：先做路线 A 验证质量，把 Provider 做成配置项。如果 A/B 对照后确认 DeepSeek 满足要求，再评估是否值得为"精确成本观测 + 强 Schema"投入路线 B 的 2–3 天。不要一上来就做 B —— 在质量未知的情况下先付重构成本，是把决策顺序做反了。

// ① CreateClient()：唯一的连接点改动
private AnthropicClient CreateClient()
{
    var key = AgentSettings.ResolveApiKey(_config);
    if (string.IsNullOrWhiteSpace(key))
        throw new InvalidOperationException("未配置大模型 API Key。");

    var client = new AnthropicClient { ApiKey = key };
    // 留空 = 走 Anthropic 官方；填 https://api.deepseek.com/anthropic = 走 DeepSeek。
    // 一个配置项即可整体回退，无需重新编译。
    if (!string.IsNullOrWhiteSpace(_s.BaseUrl)) client.BaseUrl = _s.BaseUrl;
    return client;
}

五、提案质量会下降很多吗？

先给答案：总体不会大幅下降。但"总体"这个词掩盖了结构性差异 —— 有些维度会升，有些会降，而降的那一个恰好压在本项目最在意的地方。逐维度拆开看：

逐维度说明

会变好的两项

中文技术写作。DeepSeek V4 Pro 在 SuperCLUE 中文综合评测拿到 70.98 分、国内第一，写作/摘要/多轮对话的中文流畅度与准确性都明显提升。本项目的交付物是中文《详细设计方案》与解决方案 HTML —— 这是它的主场。

长上下文检索。MRCR 1M 大海捞针 83.5%。本系统 system 前缀内联了解决方案 HTML 模版全文 + 97 个模块清单 + 章节标准，属于典型长前缀场景，这一项不会成为瓶颈。

基本持平的两项

超长文档分片生成。系统靠 write_output + 多次 append_output（每次 4000–5000 字）拼出完整 HTML/MD。DeepSeek 单次输出上限 384K token，比当前 64K 配置富余得多，分片机制本身不受影响。

指令遵循。这关系到"★必备章节一项不能少""单平台 ≤6 模组 / ≤8 托盘""阶段二耗时必须与阶段一 HTML 一致"这类硬约束。评测显示 V4 Pro 在复杂多条件语境下多 Pass 表现一致，甚至能遵守指定字数区间，接近 GPT-5.4 水平。这一项可以放心。

真正的风险：不编造参数

项目的 SOUL.md 第一条写的是"所有技术参数必须引用自 references/ 知识库，严禁编造数据；不确定时诚实说明"。system 前缀里也写了"严禁编造；不确定时明确说明并列出待补信息"。这套约束目前完全依赖模型自律。

而公开评测指出两件对本项目直接不利的事：

  • V4 Pro 在"模型不知道答案时是否承认不知道"这一口径下表现很差 —— 它几乎总是选择继续给出答案，而不是明确说"这个参数我没读到"。这与"不确定时诚实说明"的要求正面冲突。
  • 其幻觉集中出现在上下文含大量相似文本时。本系统的 system 前缀恰恰是 97 条格式高度同构的 MOD-XX-000 名称（分类） 清单 —— 这正是最容易诱发"编一个看起来很合理的模块号/参数值"的上下文形态。

后果不是"文档写得差"，而是"文档写得很漂亮但参数是编的"。对售前技术方案来说，后者的杀伤力远大于前者：客户拿方案去对国标、对设备手册，一个对不上的耗时数字或不存在的模块编号，损失的是信任。

怎么把这个风险堵住

好消息是：这是工程问题，不是模型问题。现有代码已经有校验骨架，缺的是最后一层。

  1. 补程序化参数溯源校验（最重要）。 当前 VerifyDetailPhaseGrounding()（:218-230）只检查"模型有没有 read_kb_file 读过阶段一 HTML"，不检查内容真伪。建议新增一步：从产出的 HTML/MD 里正则抽取所有 MOD-\w{2}-\d{3} 编号与带单位的数值型指标，逐一回查 references/ 卡片与 FileTools.ReadKbFiles 的实际读取记录，对不上的写入运行日志并在前端标红。这一层无论换不换模型都该做，换模型之后从"加分项"变成"必须项"。
  2. 模块选定改强制工具调用（改动清单第 4 项）。工具的 JSON Schema 约束比自由文本强得多，配合已有的 _catalog.Normalize() 存在性校验，幻觉编号会被直接过滤掉。
  3. 在 system 前缀里加显式的"不知道"授权。 对幻觉率高的模型，"严禁编造"这种否定式约束效果有限，改成正面授权更有效："读不到某个参数时，直接写『该参数需向知识库补充：<参数名>』并继续，这是被鼓励的正确做法，不是失败。" 给模型一条合法的退出路径，比堵死它更管用。
  4. 保留双模型方案作为后备。 如果 A/B 对照发现幻觉率不可接受，可以走"DeepSeek 生成 + Claude 抽检"：用 DeepSeek 跑完整个生成流程（占 95% 以上 token），再用 Claude 做一次单轮的参数溯源审查。按下节测算，这样成本仍能降到原来的约 20%，同时保住准确性底线。

关于 SWE-bench Pro 那 8.9 个百分点

DeepSeek V4 Pro 在 SWE-bench Pro 上 55.4 分，Opus 4.7 是 64.3，差距接近 9 个点，是所有对比里最大的一处。但不宜直接套到本项目上：SWE-bench Pro 考的是在陌生大型代码库里做生产级修改 —— 需要跨文件推理、理解隐式依赖、通过隐藏测试。

本项目的工具循环形态要简单得多：只有 4 个工具（两读两写）、线性的"读知识库 → 写文件 → 追加 → 收尾"流程、没有跨文件依赖推理、成败由程序化校验（HTML 数量、MD 是否产出）判定。这个形态更接近 Terminal-Bench 2.0 所测的多工具协调，那里两者只差 1.5 个点。

所以对工具循环的预期是"小幅下降"，不是"下降 9 个点"。具体表现可能是：40 轮上限内偶尔多用几轮、分片续写时偶尔重复一小段内容 —— 而代码里的 IsMaxTokens 续写引导与轮数上限保护已经覆盖了这两种情况。

2. 探针 实测 P1 不确定项：effort="xhigh" 是否被接受、ThinkingConfigAdaptive 形状是否识别、usage 缓存字段是否回填。逐项写进配置默认值。 半天 三项均有明确结论并落到配置
3. A/B 对照 选 2–3 个已交付过的真实提案（有人工确认过的正确答案），两个模型各跑一遍，用第 0 阶段的校验器 + 人工复核对比。 1 天 幻觉参数数量、★必备章节缺失数、耗时计算一致性、工具循环轮数四项指标
4. 决策 达标 → 切换，Claude 保留为配置回退项；不达标 → 转双模型方案（DeepSeek 生成 + Claude 抽检）。 — —
5. 收尾 P1/P2 项：命名与前端文案去竞品化、日志标注缓存不可见、补 DeepSeek 错误码重试判定。 半天 运行日志与前端无 Claude/Anthropic 字样

合计约 3.5 天，其中 1 天是本来就该补的校验器。把 Provider 做成配置项是这套方案的关键设计 —— 它让"换模型"从一次不可逆的重构，变成一个可以随时回滚、甚至可以按项目区分的运行时选择。

八、实测结论（2026-08-15 补录）

本节原为"基于公开文档的推断，尚未实测"。迁移实施时已对 api.deepseek.com/anthropic 逐项打了探针，结论如下 —— 其中一条推断被推翻。

⚠ 被推翻的一条：强制工具调用不能指定具体工具

第四节改动清单第 4 项原写"改用强制工具调用，配 tool_choice = tool"。实测该写法被拒：

HTTP 400  {"message": "Thinking mode does not support this tool_choice",
           "type": "invalid_request_error"}

根因：DeepSeek V4 Pro 恒开 thinking（不发 thinking 字段时，每次响应同样带 thinking 块），而 thinking 模式下不接受"必须调用某个指定工具"这种 tool_choice。

解法：改用 tool_choice = {"type":"any"}（必须调用某个工具）。模块选定这一步只定义了 submit_modules 一个工具，因此两者语义完全等价，实测可用、稳定返回 stop_reason=tool_use。代码中已在该行钉了"勿改回"的注释。

探针项结果对迁移的影响
model=deepseek-v4-pro 基线200密钥、端点、模型名均正确
effort=high / xhigh均 200都不报错。但是否真正影响推理深度无法从外部观测，故配置保守取 high
thinking={"type":"adaptive"}200可用，但 V4 Pro 本就恒开推理，发与不发行为一致 → 配置取 off，少发一个未知字段
tool_choice={"type":"tool"}400见上方红框，已改用 any
tool_choice={"type":"any"}200模块选定核心路径成立，input 结构正确
thinking 块的 signature存在（UUID）工具循环安全：多轮原样回传 thinking + tool_use 正常，两轮循环验证通过
cache_control200（被忽略）确认只是忽略、不报错，与文档一致
usage 缓存字段字段在，恒为 0成本可观测性确实变盲，日志已改为显式标注，避免运维误判
未识别模型名静默映射claude-opus-4-8 被映射到 deepseek-v4-pro；仍显式写模型名为宜
流式 + 工具 + any通过用 SDK 的 CreateStreaming 走完整两轮循环，与程序实际路径一致

仍未实测、需在真实提案中观察的三项

  • DeepSeek 自动磁盘缓存在 40 轮工具循环下的实际命中率（官方明确"尽力而为、不保证命中"，且缓存单元需完全匹配；由于 usage 不回填，只能从账单侧间接观察）
  • 中文场景下两家分词器的 token 数差异（直接影响第六节成本测算的准确度）
  • 长任务的实际吞吐与单轮延迟（现配置 TimeoutMinutes=60、MaxConcurrency=2 是否仍然合适）
